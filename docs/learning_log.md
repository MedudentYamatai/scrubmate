## Phase 0: 環境構築・Panda 読み込み・ビューア (2026-10-24)

### 学んだ概念
- **MJCF の構造**: `<worldbody>` 以下の body の入れ子が運動学ツリーそのもの。関節 (`<joint>`) は
  「親 body に対して子 body がどう動けるか」を定義する。Panda は link0→…→link7→hand→指 の直列鎖。
- **qpos / ctrl**: `qpos` は一般化座標 (Panda はヒンジ 7 + 指スライド 2 = 9 次元)。
  `ctrl` はアクチュエータへの入力。Menagerie の Panda は**位置サーボ**
  (`force = kp(ctrl − q) − kd·q̇`) なので、ctrl には目標関節角を入れる。
- **順運動学 (FK)**: 関節角 → 手先の位置姿勢。`mj_forward` で計算され、`data.xpos/xmat` に入る。
  home 姿勢で TCP = (0.554, 0, 0.521) m、TCP z 軸 = (0, 0, −1) = 真下向き。
- **mj_forward と mj_step**: forward は時間を進めずに状態から派生量 (姿勢・接触・力) を計算、
  step は timestep (2 ms) だけ積分して時間を進める。
- **オフスクリーン描画**: `mujoco.Renderer` はウィンドウ無しで描画できる。動画・合成データ生成はこちらを使う。

### 設計判断と理由
- Python 3.12 に固定: mujoco / ultralytics / torch(MPS) / mlx-whisper の wheel が揃っていて最も安全。
- Panda は `robot_descriptions` 経由で取得: commit がパッケージのバージョンで固定される
  (現在の Menagerie commit: `feadf76`)。自前でコピーするより再現性が高い。
- TCP 用の site が Menagerie の hand に無いので、hand 原点から z 方向 0.1034 m (Franka 公式) を TCP と定義 (`sim/robot.py`)。

### 詰まった点と対処
- `mjpython` が `Library not loaded: @rpath/libpython3.12.dylib` で落ちる。
  uv の Python (python-build-standalone) は libpython を rpath で引くが、mjpython の .app 経由では解決できない。
  → `DYLD_LIBRARY_PATH` に本体 Python の `lib/` を足すラッパ `scripts/mjpython.sh` で回避。

### 実験と結果
- **PD ゲインと追従誤差** (`--kp-scale 1 / 0.1 / 0.01`): 1 倍でも RMS 約 2.5°、0.01 倍では腕が持ち上がらず垂れた。
  位置サーボは「バネ」なので、重力トルクを支えるには ズレ = 重力トルク / kp が必要。kp が小さいほど大きく垂れる。
  → 把持精度に効く。実機は重力補償で打ち消す (Phase 1 で導入)。
- **肘だけ動かす FK**: 肘 −1.57→−2.4 (≈48°) で TCP は手前・下へ移動し、指の向きも真下から ≈47° 傾いた。
  home 姿勢では joint2/4/6 の軸が平行なので、肘の回転がそのまま手先の傾きになる。
  手首 (joint6) で向きを戻すと今度は TCP が 18cm 前へずれる → 位置と姿勢は複数関節で同時に合わせる必要がある = IK が要る理由。
- 外力 (Ctrl+右ドラッグ) で押すと、kp を下げた腕はバネのようにたわんで戻る。

### Q&A
- Q. 物を取るたびに関節角を人が指示する? → No。音声→LLM→検出→動作計画→**IK**→ctrl と上位から翻訳される。
  ctrl (関節角) は最下層のインタフェース。人間が考えやすい「手先の位置」とロボットが受け付ける「関節角」をつなぐのが IK。
- 公開用のコミット作者は GitHub の noreply アドレスにし、個人メールを履歴に残さない。

## Phase 1: シーン構築・IK・真値での pick & place (2026-10-24)

### 学んだ概念
- **微分 IK (DLS)**: `Δq = Jᵀ(JJᵀ + λ²I)⁻¹ e` を反復。J (6×7) は「関節を少し動かしたときの手先の動き」。
  λ は特異点 (腕が伸びきる等) で Δq が爆発しないためのブレーキ。
- **冗長性と零空間**: Panda は 7 関節で手先は 6 自由度。手先を動かさない関節の動かし方 (零空間 `N = I − J⁺J`) で
  home 姿勢へ引き戻し、肘が変な向きへ流れるのを防ぐ。
- **重力補償** (`gravcomp`): リンクごとに重力と逆向きの力を足す。静止時の TCP 誤差は 0.2mm に。
- **IK の初期値は「指令値 q_cmd」**: 実際の qpos はサーボ遅れ (動作中は最大 2cm) があるので、そこから解くと指令が揺れる。
- **MjSpec で組み立て**: Menagerie の panda.xml は編集せず attach。keyframe はシーン全体の qpos 次元を持つので、
  物体を足すと壊れる → 関節名指定で初期姿勢を入れる方式に変更。
- **接触の柔らかさ**: MuJoCo の接触はわずかに柔らかく、摩擦限界以下でもじわじわ滑る (クリープ) ことがある。

### 設計判断と理由
- 器械はローカル原点 = 重心。把持点 = 重心にすると持ち上げたときに回転モーメントが出ない。
- 支持バー間隔 ±3.5cm (当初 ±4.5cm)。ペアンは重心がリング側に寄っていて、後端がバーに 3mm しか掛かっていなかった。
- グリッパ把持力を 20 倍 (≈10N/指)。Menagerie のままだと幅 2cm を挟んで約 0.5N しか出ない。実機は最大 70N。
- 器械台は濃い青緑 (滅菌ドレープ想定)。白い天板だと銀色の器械が白飛びして検出用画像でほぼ見えなかった。
- キー入力はターミナルで受ける。ビューアは英字 26 文字すべてに表示切替のショートカットが割り当て済み。

### 結果 (真値で 5 本 × 器械台⇄トレイ往復 = 10 回)
- 成功 10/10。把持位置のずれ 平均 0.4mm、置き位置誤差 平均 2.5mm (最大 4.4mm)、向き誤差 平均 0.3°、隣の器械への干渉 0mm。

### 詰まった点と対処
- IK が器械台側で 0.7mm 残って収束しない → 零空間射影にダンピング付き擬似逆行列を使っていたため、
  姿勢の引き戻しが手先に漏れていた。ダンピング無しの `pinv` に変えて 0.1mm 以下に。
- 把持中の滑り 2〜4mm (メスで最大)。原因を切り分けた結果:
  摩擦係数・把持力・noslip・制御周期 (10ms→2ms) では変わらない / 接触を柔らかくすると増える /
  **指が閉じる方向に運ぶときだけ発生** (長手方向に運ぶと 0.3mm、ペアンはほぼ 0)。
  → 接触のクリープと推定。置き位置誤差 (<1cm) の許容内なので深追いせず、制限事項として記録。
- テスト中に mjpython の GUI が起動途中で止まるようになった (画面スリープ等の環境要因と推定)。遠隔操作は偽ビューアで検証。

### 実験と結果 (自分で実行)
- **重力補償を切る** (`--only pean --no-gravcomp`): 静止時の TCP 誤差 0.2mm → 6.6〜8.3mm、把持位置のずれ 0.4 → 3.7mm。
  それでも成功 (2/2)。指の開き 55mm・成功基準 1cm に対して 7mm は小さいため。ただし Phase 3 では知覚の誤差が上乗せされる。
- **把持力を Menagerie の初期値に戻す** (`--only scissors --grip-scale 1`): 指は剪刀に触れている (閉じた幅 16mm) が、
  押しつける力 ≈0.5N では 114g (≈1.1N) を摩擦で支えきれず、手だけが上がって剪刀は台に残った (0/2)。
  このとき `slip=342mm` は「滑った」のではなく「台に残った器械と手の距離」。紛らわしいので失敗理由の表示を追加。
- **遠隔操作で前へ伸ばし続ける**: 目標 x=2.08m (届く範囲は約 0.9m) で IK 誤差 1.19m、特異値 min は home の 0.30 → 0.12。

### Q&A
- Q. 特異値 min とは? → ヤコビアンを特異値分解すると「関節を 1rad 回したとき手先が各方向に何 m 動くか」が 3 方向ぶん出る。
  最小値 = いちばん動かしにくい方向の動かしやすさ。0 なら特異点 (その方向へ手先を動かせない)。
  前へ伸ばすと min が下がり、その方向はほぼ x (前後) = 腕を伸ばしきると、それ以上前へ出せない。
  手先を真下に向ける条件があるので 0 までは下がらない。
- Q. 動画は人が操作したもの? → いいえ。プログラムが自律的に動かしている。ただし器械の位置をシミュレーターの真値から
  もらっている (= ズル)。Phase 2〜3 でこれをカメラ画像からの推定に置き換えるのが本題。
- Q. ロボット学習は遠隔操作で軌道を集めて学習するのでは? → それは模倣学習 (end-to-end。SmolVLA・ACT など)。
  今回は「見る (YOLO を学習)」「理解する (Gemini)」「動く (IK + 手順。学習しない)」を分けるモジュラー型。
  仕様の指定・失敗理由を説明できること (器械カウントは安全に関わる)・締切 の 3 点から。模倣学習との比較は発展課題。

## Phase 2: 合成データ生成と YOLO-seg 学習 (2026-10-25)

### 学んだ概念
- **segmentation レンダリングで自動ラベリング**: MuJoCo は各ピクセルに写っている geom の ID を描画できる。
  geom → body → 器械名 と辿れば正解マスクが手に入る。輪郭 (`cv2.findContours`) を YOLO-seg の多角形ラベルにする。
- **ドメインランダム化**: 照明・天板/バー/トレイの色・金属の明るさ・カメラの位置/角度/画角・ノイズ・腕の写り込みを毎枚変える。
  変わらない手がかり = 形 だけを覚えさせる。sim2real の基本の工夫。
- **転移学習**: COCO で学習済みの yolo11n-seg から出発。1 エポック目で mask mAP50 0.97。
- **mAP50 と mAP50-95**: 前者は「見つけたか」、後者は「形・位置がどれだけ正確か」。
- **しきい値と混同行列**: mAP は確信度の低い予測まで全部使う。混同行列はしきい値 0.25 で数えないと、ゴミ予測が誤検出として千件入る。

### 設計判断と理由
- 器械の置き場は器械台 5 + トレイ 3。欠品 (1〜5 本)、位置 ±1cm、30% は逆向き (yaw=π)。
- 15% の画像は腕を器械台の上に出して器械を隠す。腕が画面の大半を覆うので 20% から下げた。
- 画像は 1024×768 (4:3) で生成し、学習は imgsz 640。
- 60 エポックの予定だったが、4 エポックで mAP50 0.99 に達したので 30 エポック + 早期終了 (patience 10) に短縮 (約 45 分)。
- 撮影中の腕は待避姿勢 `PARK_QPOS` (`sim/robot.py`)。

### 結果 (検証 300 枚)
- box mAP50 0.995 / mask mAP50 0.995 / mask mAP50-95 0.854。
  mask mAP50-95 が最も低いのは鑷子 (0.765)、最も高いのは剪刀 (0.915)。細い器械ほど輪郭の精度が出にくい。
- 混同行列 (conf 0.25): 種類の取り違えは 1,062 本中 4 本。見逃し 7、誤検出 16。
- 画像ごとの種類・本数の完全一致: 全体 95.0%、**腕を待避した画像 100% (251 枚)**、腕が器械台の上にある画像 69.4% (49 枚)。
  腕の失敗は、隠されて 1 本が 2 つに分かれ二重に数える、ほとんど隠れた器械を見逃す、の 2 種類。
  → カウントは必ず腕を待避させてから撮る (Phase 5 の設計に反映)。

### 詰まった点と対処
- ultralytics に相対パスの project を渡すと `runs/segment/runs/segment/...` に保存される → 絶対パスで渡す。
- 学習済み重みに学習時の絶対パス (ユーザー名入り) と git 情報が埋め込まれていた → 書き出し時に消し、残っていないか検査。
- ultralytics の利用統計の送信 (sync) を切った (`yolo settings sync=False`)。

### 実験と結果 (どれも本番と同じ「見た目がばらばらな」検証 300 枚で評価)
| | 本番 (ランダム化あり・1200 枚) | ① ランダム化なし (1200 枚) | ② データ 1/6 (200 枚) |
|---|---|---|---|
| mask mAP50 | 0.995 | 0.975 | 0.994 |
| mask mAP50-95 | 0.854 | 0.759 | 0.823 |
| カウント一致 (腕を待避) | 100% | 91.2% | 99.2% |
| カウント一致 (腕が器械台の上) | 69.4% | 34.7% | 65.3% |
| 見逃し / 誤検出 (conf 0.25) | 7 / 16 | 37 / 51 | — |
| 学習時間 | 45 分 | 45 分 | 7 分 |

- **① ランダム化なし**: 学習中の検証 (学習と同じ見た目) では mAP50 0.995 だったのに、見た目が変わると全指標が落ちた。
  最も見逃したのはメス (18 本)。形が単純な棒なので、見慣れない天板の色や照明では背景のバーと区別しにくい。
  学習で一度も見ていないロボットの手首のボタンを「剪刀」と誤検出した。
  天板の明るさ別に見ても失敗率は同じ (約 9%) で、特定の色だけが苦手なのではなく、見慣れない条件全般に弱い。
  注意: ランダム化なしのデータには腕の写り込みも無いので、「腕が器械台の上」の 34.7% は腕を見たことがない効果も混ざっている。
- **② データ 1/6**: 200 枚でも mAP50 0.994、待避時のカウント 99.2% とほぼ同等。輪郭の正確さ (mAP50-95) だけ 0.03 下がった。
  → 「枚数を増やす」より「見た目を散らす」ほうが効く。5 種類の単純な形を見分けるだけなら、ランダム化さえあれば数百枚で足りる。

## Phase 3: カメラの推定で掴む (2026-10-26)

### 学んだ概念
- **ピンホールカメラと逆投影**: 焦点距離 f = H / (2 tan(fovy/2)) [px]。画像中心から (du, dv) px の画素は、奥行き Z で (du·Z/f, dv·Z/f) m 光軸から離れる。
  画像 1 枚では「どの方向か」しか分からず、深度で「何 m 先か」が決まる。MuJoCo の深度は光軸方向の距離 (器械台中央で 0.840m = カメラ高 1.55 − 天板 0.71 と一致)。
- **主成分分析 (PCA) で向き**: マスクの点の共分散行列の固有ベクトルのうち、分散最大の方向 = 長手方向。前後 (先端がどちらか) は区別できない。
- **透視投影の歪み**: 斜めから見える部分は側面まで写るので、厚い所ほど画像上で太く見える。深度で各画素の本当の 3D 位置に置き直すと消える (真上から見た地図)。
- **冗長自由度**: Panda は 7 関節で、手の位置・向き (6 自由度) より 1 つ多い。同じ手先でも腕の構えが無数にあり、IK は初期値に近い構えを返す。
- **手首の軸と手の yaw**: joint7 の回転軸は手先 (TCP) を通る。手が真下を向いていれば、joint7 だけで手の yaw が回り、手先の位置は変わらない (yaw +θ = joint7 −θ)。
  joint7 の可動域は ±166° (332°) なので、どの場所でも手を向けられない yaw が約 28° ある。

### 設計判断と理由
- 先端の判定は「マスクの形の偏り」(ユーザーと相談して決定)。長手方向に沿った**外形の幅のプロファイル**を、器械の形状モデル (`make_shape`、実機ならカタログ寸法) と照合する。
  面積でなく外形の幅にしたのは、鑷子 (V 字) は面積が前後でほぼ同じでも外形の幅は先端側が広いから。
- 撮影は掴む直前に毎回、腕を待避姿勢にしてから (ユーザーと相談して決定)。Phase 2 で待避時のカウント一致率が 100% だったため。
- 把持点 = 面積の重心 + 形状モデルから計算した「面積の重心 → 質量の重心」の補正。メスは刃が薄いので、面積で見ると重心が刃側に 13mm 寄る。
- 真値は `--gt` の比較と評価にだけ使う。`--gt` も同じく待避姿勢を経由させ、違いを「把持目標の出どころ」だけにした。
- 返却トレイの中の向きは問わない (実シナリオでトレイに置くのは術者)。器械台には先端 +x に揃えて置く。

### 結果
- 推定精度 (`perception/eval_locate.py`、学習データと同じ分布のランダム配置 50 通り × 5 本 = 250 回): 見逃し 0、
  位置誤差 平均 2.1mm / 最大 9.0mm、高さ誤差 最大 0.3mm、長手方向の軸の誤差 平均 0.31° / 最大 4.7°、**先端方向の正解率 100%**。
- pick & place (`control/pick_place_demo.py --trials 30`、ランダム配置 30 通り × 5 本 × 往復 = 300 回): **成功 300/300**。
  推定の位置誤差 平均 2.5mm、置き位置誤差 平均 2.9mm / 最大 8.1mm、置き向き誤差 平均 0.6° / 最大 4.7°。
  トレイで先端が逆向きだった 45 回は、45 回とも器械台に正しい向きで戻せた。
- 既定の配置では、知覚ベースも真値 (`--gt`) も 10/10。

### 詰まった点と対処 (失敗 → 原因 → 対処)
1. 重心が剪刀で 6mm、鑷子で 7mm ずれた → YOLO のマスクは外形の多角形なのでリングの穴や腕の隙間も塗られているのに、
   比べる形状モデルは穴あき・box の重なりを二重に数えていた → 形状モデルも同じ処理 (方眼に塗る → 細い隙間を閉じる → 外形で塗りつぶす) で作る。
2. メスの重心が柄側に 3mm ずれた → 透視で柄 (厚さ 1cm) の側面まで写り、柄が太く見えていた → 深度で真上から見た地図 (1mm 方眼) に描き直す。
   正解マスクで試すと全器械で誤差 1.3mm 以内になった (残りは YOLO の輪郭の精度)。
3. 明るいトレイの上でメスの先端を逆に判定 (250 回中 1 回) → 刃が背景に溶けてマスクから欠け、幅のプロファイルが前後対称に見えた →
   マスクの外側 5px 以内で、支持バーより高い画素を器械として足す (深度でマスクを補う)。範囲を狭くしたのは、トレイの壁が器械の上面と同じ高さ (0.76m) だから。
4. トレイから器械台へ戻すと 30° 斜めに置かれた → 器械を 180° 回すとき手首 (joint7) が限界 (±2.90 rad) に当たっていた →
   掴み方 (手の yaw か +180°) と回す向き (右回り / 左回り) の 4 通りから、手首に余裕がある組み合わせを選ぶ (`plan_transfer`)。
5. それでもランダム配置で 3〜8/10 → IK が「手首は限界に張り付き、他の関節をねじって向きを合わせた構え」を返していた (冗長自由度) →
   場所ごとに素直な構えを 1 つ IK で求め、手の yaw は joint7 だけで回す (手首の軸が手先を通るので計算で求まる)。真上へは関節空間で直接動く。
   これで隣の器械を押す失敗も消えた (ねじれた腕が当たっていた)。
6. 器械台の右端から「先端 180° 向き」でトレイに置く組み合わせは、手首の可動域が足りず解が無かった (30 配置中 5 配置) →
   トレイの中の向きは問わないことにした (実シナリオに無い動作だったため)。実機なら持ち替え (一度置いて掴み直す) で対処する。
7. (ユーザーの指摘) 動画で、待避姿勢の腕が術野側 (+y) に出ていて術者の邪魔になりそう → 待避の向きを反対側 (−y) に変えた (`sim/robot.py` の `PARK_QPOS`)。
   カメラに写る腕の画素はどちらも 0。手と術野中心の距離は 0.35m → 1.24m。変更後も推定精度は同じ、pick & place は 300/300。
   学習データは旧い待避姿勢で作ったが、腕は画像に写っていない (影だけ) ので再学習は不要だった。

### 実験と結果 (自分で実行)
- **① 置き方のばらつきを学習データの 2 倍に (位置 ±2cm・向き ±12°)** `eval_locate --spread 2`:
  見逃し 0 → 4 本、位置誤差の最大 10.6 → 16.3mm、先端方向の正解率 100 → 99.6% (250 本中 1 本)。平均はほぼ同じ (2.1 → 2.6mm)。
  悪化した例はすべて**返却トレイの中で器械どうしが重なった・交差した**配置 (トレイの置き場の間隔 7.5cm に対し、リング付き器械の幅は 5cm)。
  2 本のマスクが混ざって重心がずれる、下の器械がほぼ隠れて見逃す、メスがトレイの壁に立てかかって 12° 傾く、など。
  器械台の上 (間隔 9cm・バーの上) では 2 倍ずらしても問題なかった。
  → 重なりは推定の弱点。Phase 6 のシナリオでは、術者の手がトレイ内の空いた置き場に返すようにする。
- **② 知覚ベースと真値の比較 (同じランダム配置 10 通り × 10 回)** `pick_place_demo --trials 10` と `--gt`:
  成功はどちらも 100/100。掴んだ位置と器械の重心のずれ (grasp_offset) は 1.95mm vs 0.56mm で、知覚の誤差 (約 2mm) がそのまま出た。
  一方、置き位置のずれ (place_err) は 2.74mm vs 2.45mm で、0.3mm しか違わない。
  置き位置のずれの大部分は、真値で掴んでも起きる「指が閉じる瞬間や離す瞬間に器械が少し動く」分で、知覚の誤差はそれに埋もれる程度。
- **③ ビューアで実時間再生**: 毎回、腕を術野の反対側にどけてから掴みに行くのを確認した。
